## Your task repository

[Source page](https://project-hertz-instructions.learn.joinhandshake.com/structure)

Every task has its own private GitHub repository named hertz-<task_code>, for example hertz-HTZ-T017. You fork it and open pull requests into it. Nothing of substance is typed into the HAI platform; the repository is the record.

```text
hertz-HTZ-T017/                 (branch: main)
├── README.md                   # the short version of this site's steps, with exact git commands
├── attempt1/                   # YOUR brief, one .txt per field  ← added by your Attempt 1 pull request
├── templates/
│   ├── attempt1/               # copy this folder to attempt1/
│   └── attempt2/               # copy this folder to attempt2/
├── schemas/                    # what every field means and what the check enforces
├── examples/                   # a complete attempt1/ and attempt2/
├── tools/validate.py           # the same checks the pull request runs; run it before you push
└── .github/workflows/          # the checks the pull request runs (do not edit)

hertz-HTZ-T017/                 (branch: codebase)
└── (empty)                     # YOUR archive goes here  ← added by your codebase pull request
```

Copy

### Two branches, three pull requests

| When | Pull request | Into branch | Contains | Title |
| --- | --- | --- | --- | --- |
| Attempt 1 | Codebase | codebase | the one archive (.zip, .tar or .tar.gz) you will mount, nothing else | &lt;task_code&gt; codebase |
| Attempt 1 | Attempt 1 | main | the attempt1/ folder: the brief | &lt;task_code&gt; attempt1 |

### What goes in attempt1/

| File | What it holds | Where it ends up |
| --- | --- | --- |
| meta.txt | key: value lines: task_code (must match the repository name), tier (t2, t3 or t4), watching_mode (live or away), codebase_pr_url, codebase_commit_sha (the full 40-character commit of your codebase pull request), codebase_source (own, oss_used or oss_other) | Read by the check and the reviewer; not pasted |
| task_description.txt | What you are trying to get done, for a reviewer who was not there | Taiga: Task description |
| how_to_judge_completion.txt | Commands to run, behaviour to check | Taiga: How to judge completion |
| reviewer_notes.txt | Anything else that helps assess the outcome; required | Taiga: Other notes for the reviewer |
| mount_source.txt | One line: the real origin of the code, never this repository or a task code | Taiga: "Where did this file come from?" when you mount |

### Validate and submit

Run the validator before pushing. Follow Submit the brief for Attempt 1.

The check requires one paperwork file per PR, a matching task code, complete fields, no secrets, and a valid codebase PR and pinned commit. All three pull requests stay open until the task is delivered; never merge or close them.

## Fork your task repo

[Source page](https://project-hertz-instructions.learn.joinhandshake.com/setup/fork)

You have read access to your task repository; you propose changes through pull requests from your own fork.

### Fork and clone

1

##### Accept the invitation

After you claim a task on HAI you receive a GitHub invitation to hertz-<task_code>. Accept it. The repository link is in your HAI task.

2

##### Fork, keeping both branches

Click Fork. When GitHub asks, untick "Copy the main branch only", so the empty codebase branch comes with it. Fork to your own account.

3

##### Clone your fork

git clone https://github.com/<you>/hertz-<task_code>.git and cd into it. Confirm both branches exist: git branch -r should list origin/main and origin/codebase.

```text
git clone https://github.com/<you>/hertz-HTZ-T017.git
cd hertz-HTZ-T017
git branch -r
# expect: origin/codebase  origin/main
```

Copy
If the codebase branch is missing

You forked with "Copy the main branch only" ticked. From inside your clone, fetch the task repository's branch: git fetch https://github.com/Handshake-project-hertz/<this repository>.git codebase && git checkout -b codebase FETCH_HEAD, then git push -u origin codebase. Never start it with git checkout --orphan: GitHub refuses a pull request from a branch with no history in common with codebase. Do not branch it from main either: it would carry the README, templates and tools into your codebase.

### Branch names you will use

| Branch in your fork | Based on | Pull request into |
| --- | --- | --- |
| codebase | the empty codebase branch | this repository's codebase |
| attempt1 | main | this repository's main |
| attempt2 | main, synced (never attempt1) | this repository's main |

Before branching attempt2, update your fork's main (or press Sync fork on GitHub):

```text
git checkout main
git pull https://github.com/Handshake-project-hertz/hertz-HTZ-T017.git main
git checkout -b attempt2
```

## Run the validator

[Source page](https://project-hertz-instructions.learn.joinhandshake.com/setup/validator)

tools/validate.py runs the pull request's checks locally. Run it before every push.

```text
# from the root of your clone, on the branch you are about to push
python3 tools/validate.py attempt1
python3 tools/validate.py attempt2
```

Copy

It prints no blocking issues, or every BLOCKING issue, marked must fix or fix or explain, and every suggestion, each with its file. A reviewer reads the suggestions.

Good

| attempt1/: no blocking issues

Bad

| attempt1/: 1 blocking issue(s), 1 suggestion(s)

- BLOCKING (must fix) attempt1/task_description.txt: too short: 140 characters, minimum 200
- suggestion attempt1/how_to_judge_completion.txt: no command or code visible; the strongest checks are commands a reviewer can run

Every blocking line names the field and the fix. The network checks (does the commit exist on the codebase pull request, does the tree contain paperwork) need internet; pass --no-network to skip them offline and let the pull request run them.

The validator infers your task code from the repository name

Run it inside your clone of hertz-<task_code> so it can check task_code against the repository. Outside a clone, pass --task-code HTZ-T017 explicitly.

## 2 · Choose your task

[Source page](https://project-hertz-instructions.learn.joinhandshake.com/workflow/step-2)

### What the instructions require:

A good task is real and checkable: something you actually want done, like the work you do every day. Use your own code, open-source code, or code you write for this task, and make sure it is safe to share. No PIIs, No old GitHub PR already solved by a human.

Start from code you work with. Good tasks look like:

- Add a feature
- Fix a bug
- Refactor
- Write tests
- A multi-part feature
- A bug that needs tracing
- A refactor across several files

Don't engineer traps. If you'd be annoyed to get the task from a colleague, it's a trap. Writing the way you normally write is not.

### Where the code comes from

| Source | What reviewers expect | What you record |
| --- | --- | --- |
| Your own code you are allowed to share | Strip secrets and anything you do not own. | source: own |
| An open-source repository you use or contribute to | Work an open issue or an improvement you would make. If a person has published a fix, it is out. | source: oss_used |
| An open-source repository you do not normally work with | Allowed, but a reviewer will ask why you want this done. If the answer is "I don't," it is role-play. | source: oss_other |

The published-fix check

Before you commit to a task on open-source code, search the repository's issues and pull requests, open and merged, for the change you plan to ask for.

### The machine your task runs on

Pick a task whose code installs, builds and tests there.

|  |  |
| --- | --- |
| Installed (as of Nov 5) | Ubuntu 24.04 on x86-64, 4 CPUs, 16 GB of memory; Node 22.21 (npm 10.9, pnpm 10.34); Python 3.10 to 3.14 (pip, uv); Java 21 (Maven 3.8, Gradle 8.14); GCC 13, make, CMake 3.28; PostgreSQL 16 (not started); Chromium (Playwright 1.56) |
| Missing | Docker, a GPU, Go, Rust, .NET, Ruby, PHP, yarn, clang, MySQL, MongoDB, Redis, among others. System packages, such as C/C++ development libraries, cannot be installed. |
| No internet | Libraries install only from internal copies of npm, PyPI, Maven and Gradle. These lack some versions, including most npm package versions under two weeks old. With a lockfile, one missing version stops the install; a commit whose lockfile is at least three weeks old helps, but is no guarantee. Every other download fails: installers, the Gradle wrapper, git dependencies, browsers, binaries. |

Check this before you pick a task

Compare your project's tools, versions and lockfile with the list above.

- Make it iterative: the job schema after the manifest validation, the edge cases after the core behaviour. State every requirement in the task description field and never say that more will come later.
- Verification is real work: a test suite, a reproducibility check, a byte-identical diff.

### Before you move on

- I actually want this done, and it is like my day-to-day work

## 4.2 · How to judge completion

### A passing command can still check the wrong thing

Completion field from an accepted sqlite-utils task. The full submitted passage follows.

Work from the mounted project root, expected to be /workspace/sqlite-utils, on Python 3.12 or later. Install the project in editable mode with its dev dependency group, for example with pip install -e . --group dev or with uv.

Note that the tool routes an unknown subcommand to its default query command, so the help command above exits 0 even before the feature exists. The usage line it prints must name import-batch, not query.

Also run the repository checks defined in the Justfile and CI in their existing scopes, which are black, flake8, mypy, pyright, ty, cog and codespell, plus the isolated no dev group help smoke check with uv run --isolated --no-default-groups sqlite-utils --help. A clean mypy result alone is not enough because mypy ignores the CLI module and the tests.

Behavior to check with fresh temporary databases and small synthetic inputs. A manifest with several valid jobs commits every job and the reopened database shows all rows. A manifest whose last job fails after earlier jobs already ran leaves the reopened database with its previous rows and schema, including earlier upserts, truncation, newly created tables and columns added by alter. An invalid manifest or an unreadable input is rejected before any write and before stdin is consumed, and a missing destination stays absent. A dry run of a valid or a failing manifest leaves an existing destination logically unchanged and a missing destination absent. JSONL, CSV and TSV jobs keep processing batches while input remains unread. Foreign key enforcement is on for the new command, a reference resolved by a later job is accepted, and an unresolved reference fails the whole batch. With JSON output, stdout holds exactly one JSON object whose outcome matches the actual database state and the process exit code, and earlier jobs are never reported as durably committed after a later failure.

Review the new command in sqlite_utils/cli.py and any focused helper module, the new tests, the CLI help text and the updated user and generated reference documentation. Confirm the existing insert and upsert commands still behave as before. Reopen databases after each command returns rather than trusting the command's own output.

Tip: The original names an environment path: in your own field, omit /workspace paths, and give the working directory and every setup step as Write the brief explains. Specify each command, expected result, and misleading success signal.

PRACTICE: IS EXIT 0 ENOUGH?

The reviewer runs the help command and gets exit 0, but its usage line names query rather than import-batch. Has that check passed? What should the completion field tell the reviewer to inspect?

CRITIQUE

No. This tool can route an unknown subcommand to query and still exit successfully. The check must name the expected usage line as well as the command. Likewise, reopening a database verifies its actual state independently of the command’s report.

Key lesson

For each check, specify what to run, what to inspect, and what counts as a pass.

Open the task, which is back at the stage that was rejected. Re-enter the fields and submit for review. The task returns to the same review stage.

3

##### Note the cycle

This was cycle 2 or 3 of that stage. If it is cycle 3 and the reviewer rejects again, the claim may be removed.

- The newest Automated pre-check on the pull request I am resubmitting has no blocking issues, or my reply to every fix or explain item
- Every reviewer comment I acted on is resolved or replied to on the pull request
- Resubmitted on HAI with fields that match the pull request

## Avoid brief and codebase pitfalls

[Source page](https://project-hertz-instructions.learn.joinhandshake.com/pitfalls)

Use this page before Review 1.

### Mentioning the project anywhere

The most common reason a task is rejected today.

Never mention this project or its process: the task is rejected immediately

One mention of this project or its process anywhere in the task form gets the task rejected.

Never write:

- the project's name (Hertz, Project Hertz), Handshake, HAI, a task code such as HTZ-T017, the task repository or its pull requests;
- our file and folder names: attempt1/, attempt2/, meta.txt, task_description.txt, how_to_judge_completion.txt, reviewer_notes.txt, first_message.txt, finish_notes.txt, mount_source.txt;
- our process words: "the brief", "task brief notes", "pre-check", "Automated pre-check", "validator", "Review 1", "Review 2", "audit", "sent back";
- anyone on our side: your project lead, a reviewer by name, "the Hertz reviewer", "as the reviewer asked".

Every field stands alone. Never point from one field to another ("see the task description", "as in the notes", "described above"). Write what the reader needs right there, as if that field were the only thing they will read.

### The codebase leaks the project

A README that mentions the task code, an attempt1/ folder copied along, our .github/workflows/validate.yml, a templates/ folder. Usually from branching codebase off main or copying the clone root. Rebuild the archive from the code alone and push it again.

### A published fix exists

An open-source issue that a person already fixed in a merged pull request. Search issues and pull requests, open and merged, before you commit to the task, and say in your task brief notes that you did.

### The judging section is prose

❌ "Check that the import works and the tests pass."

✅ python -m pytest -q tests/test_cli_import_batch.py must pass; a manifest whose last job fails leaves the reopened database with its previous rows; the --help command exits 0 even before the feature exists, so check the usage line names the command.

A reviewer runs your checks. Give them commands and observable outcomes on fresh inputs, and name the caveats.

Before you submit the brief

Check the scope and verification criteria, then review Before you submit.

What is paid

You must score at least 75% to pass

You must score at least 75% to pass the CodeSignal assessment. If you do not pass, you are automatically offboarded from Project Hertz. There is one attempt and no retake, so block out the full 2 hours and read this page before you start.

### Eligibility

You need at least 4 years of professional software engineering experience and a degree in computer science or a related field. No specific programming language is required.

### The assessment

The Project Hertz technical assessment checks both how you solve problems and how you reason about your solutions. The assessment is worth 500 points in total.

Code review
100 points
One question. Review a small, focused pull request as you would a teammate's. Read the engineering context behind the diff so you know what to look for.
System design writing
100 points
One question. Compare two background processing designs and identify at least 5 weaknesses in the weaker approach and 5 strengths in the better one.
Coding (data structures and algorithms)
100 points
One coding question. Timing can vary with your approach.

The total time limit is 2 hours, so plan your time to finish every part.

one sitting, you cannot pause once you start
1 attempt
there is no retake

recorded for the whole assessment
1 to 3 business days
to hear your result, proctoring review included

We value clarity, correctness and careful reasoning. The goal is not only a correct answer, but a clear account of how you got there.

- Block out the full 2 hours before you start.
- Use the same email as your Handshake AI account, or your result may not reach us.
- Keep your face in view and stay on the assessment window.
- Choose somewhere quiet with other apps and tabs closed.

## Tasks and reviews

[Source page](https://project-hertz-instructions.learn.joinhandshake.com/faq/inplatform/task-access)

### How many tasks can i hold at once?

Two, until two of your tasks are fully approved; then five. A slot opens when a task is approved or you release it.

### Can i use my employer's code?

Only if you are allowed to share it. No private code you cannot publish, no secrets, no personal data. If in doubt, use an open-source repository you use.

### Can i use the same codebase for more than one task?

Yes, if each task is different work. Prepare the codebase branch from each task's own pinned state.

### Why does the codebase live on a separate branch?

The codebase branch holds only your code, the zip you mount comes from it alone, and the check blocks a codebase that contains paperwork.

### How long does a review take?

12 to 24 hours, sometimes more.

### My task came back. Where is the feedback?

In review comments on your pull request, on the file and line.

### What happens after three review cycles?

The reviewer may remove your claim; the task leaves your queue and is not paid. Fellows whose tasks reach that point repeatedly are offboarded.

### The platform shows a quality check on my task

Open the checklist icon in the task's top-right corner and fix, or disagree with reasons, each flagged item. Resolve every one before continuing.

### What should i do if i keep getting "Failed to submit task/block"?

Try these in order:

1. Check the fields. Every required field filled, every confirmation ticked, the pull request links in full.
2. Wait and try again. Refresh, wait a little, resubmit.
3. Check your browser. Use Google Chrome; try an incognito window or clear cache and cookies.
4. Check your device. Restart. Don't use a mobile device or Chromebook.

### Which account do i use to sign in to taiga?

The firstname@handshakefellows.ai Google account Handshake creates for you, through Sign in with Google; your personal account will not work. Steps: Intro to Taiga.
